# Elasticsearch 叢集健康檢查使用手冊

本工具只讀取使用者指定的 Elasticsearch／Kibana API，不執行修復。使用者可選兩條路線；兩者使用相同的診斷邏輯。

本手冊所稱「採集包」，是指由 `collect.sh` 產生、供離線分析使用的診斷資料採集包（Bundle）。

| 路線 | 使用者端需要執行 | 適用情境 |
|---|---|---|
| A：Live | `elk-diagnostics` binary | 允許執行已核准 binary，且分析機可連 ES |
| B：採集包 | 可審閱的 `collect.sh` | 使用者端禁止未知 binary，交由分析端產報告 |

## 1. 前提與安全

- ES 8.4 以上可使用完整 `_health_report`；較舊版本的部分項目會標示 `skipped` 或版本警告。
- 連線標準：HTTPS、自簽 CA（若使用）、Basic Auth；正式環境請使用企業秘密管理系統。
- 不要把密碼寫入命令列、shell history、`config.yaml` 或版控。互動輸入不回顯。
- `--insecure` 僅限測試，不適用正式環境。
- 報告是唯讀診斷引導，不等於已確認根因或自動修復。

### 1.1 預期 ES 節點清單（選配）

若要偵測「檢查或採集開始前已離線」的節點，請在實際執行 binary 或 `collect.sh` 的交付包目錄建立清單。`make dist` 會提供範本 `expected-es-nodes.txt.example`。

```bash
cd /交付包實際路徑
cp expected-es-nodes.txt.example expected-es-nodes.txt
```

接著用文字編輯器開啟 `expected-es-nodes.txt`，每行填入一個現場已知的 ES `node.name`；不要直接使用範例名稱，也不要填 IP 或 roles：

```text
es8-mn1
es8-mn2
es8-mn3
```

這份清單是執行前依現場拓撲建立的基準，不應直接提交或沿用到另一個叢集。未建立清單時，其他檢查仍會執行，但「預期 ES 節點完整性」會標示 `skipped`。IP 與 roles 仍由 ES API 自動取得。

需要的工具：

```bash
./elk-diagnostics version   # 分析端
command -v curl              # 採集端
```

## 2. Route A：Live 直連

可用 `config.yaml`、環境變數或 flags；優先序為 `flags > 環境變數 > config.yaml`。

### 2.1 設定連線

正式環境建議使用不含密碼的 `config.yaml`：

```bash
cp config.yaml.example config.yaml
```

填入 ES host、帳號與 CA 路徑，並確認 `insecure_skip_verify: false`。臨時操作也可使用：

```bash
export ELK_DIAGNOSTICS_HOSTS='https://es.example.local:9200'
export ELK_DIAGNOSTICS_AUTH_TYPE=basic
export ELK_DIAGNOSTICS_USERNAME='elastic'
export ELK_DIAGNOSTICS_CA_CERT="$PWD/ca.crt"
```

執行時省略密碼，binary 會在 Terminal 安全詢問：

```bash
mkdir -p reports
./elk-diagnostics check \
  --output html \
  --output-file reports/check.html \
  --metrics-output reports/metrics.ndjson
```

若已依 §1.1 建立清單，於 `check` 加上：

```bash
--expected-es-nodes-file "$PWD/expected-es-nodes.txt"
```

路徑必須指向目前工作目錄中的 `expected-es-nodes.txt`；若檔案不在該處，請改用絕對路徑。未提供清單時，報告會明確標示此項 `skipped`。

`metrics.ndjson` 是長期趨勢用的結構化觀測值；HTML 是單次判讀報告，並在具有可靠數值來源的診斷卡顯示該次關鍵觀測值。純開關或狀態型檢查只呈現判定結果，不會為了趨勢輸出而硬轉為 `0/1`。

單次覆寫可用 flags：

```bash
./elk-diagnostics check \
  --host 'https://es.example.local:9200' \
  --username elastic \
  --ca-cert "$PWD/ca.crt" \
  --output text
```

### 2.2 症狀診斷

只有 Live 路線可直接執行症狀樹：

```bash
./elk-diagnostics diagnose --symptom red-cluster --output text
./elk-diagnostics diagnose --symptom write-bottleneck --output text
```

### 2.3 清除臨時設定

```bash
unset ELK_DIAGNOSTICS_HOSTS ELK_DIAGNOSTICS_AUTH_TYPE
unset ELK_DIAGNOSTICS_USERNAME ELK_DIAGNOSTICS_PASSWORD
unset ELK_DIAGNOSTICS_CA_CERT ELK_DIAGNOSTICS_API_KEY ELK_DIAGNOSTICS_TOKEN
```

## 3. Route B：採集包後離線分析

採集端不需要 Go、jq 或 binary；分析端不需要連線使用者的 ES。兩階段必須分開。

### 3.1 使用者端採集

若要找出採集前已離線的節點，先依 §1.1 在 `collect.sh` 同一目錄建立固定檔名 `expected-es-nodes.txt`。以下指令的 `--expected-es-nodes-file` 可省略；省略時不影響其他檢查。

```bash
export BUNDLE_ROOT="$PWD/bundle-$(date +%Y%m%d-%H%M%S)"

./collect.sh \
  -h 'https://es.example.local:9200' \
  -u elastic \
  --ca-cert "$PWD/ca.crt" \
  --expected-es-nodes-file "$PWD/expected-es-nodes.txt" \
  -o "$BUNDLE_ROOT"
```

採集腳本會將這份清單複製到採集包根目錄的 `_expected_es_nodes.txt`；分析端會自動讀取，不需要再次傳入清單路徑。

互動模式會安全詢問密碼。非互動式採集請由秘密管理系統提供權限 `600` 的檔案：

```bash
ES_PASSWORD_FILE=/run/secrets/elasticsearch-password ./collect.sh \
  -h 'https://es.example.local:9200' -u elastic \
  --ca-cert "$PWD/ca.crt" -o "$BUNDLE_ROOT"
```

採集完成後確認：

```bash
test -f "$BUNDLE_ROOT/elasticsearch/version.json" &&
test -f "$BUNDLE_ROOT/_manifest.json" &&
test -f "$BUNDLE_ROOT/_status.txt" &&
echo '採集包基本結構：OK'
```

顯示 `採集包基本結構：OK` 代表三個必要檔案都存在；未顯示 `OK` 或出現錯誤即未通過，請先確認 `BUNDLE_ROOT` 是否指向本次採集包根目錄。

#### 選配：增加 Host／Kibana／Logstash 證據

`collectors/` 必須與 `collect.sh` 放在同一目錄。未指定 `--services` 時仍只採集 ES，現有流程不變。

互動式 Terminal 採集 Kibana（未提供密碼檔時會不回顯詢問密碼）：

```bash
export KIBANA_USERNAME='elastic'
unset KIBANA_PASSWORD_FILE KIBANA_API_KEY

./collect.sh \
  --services es,kibana \
  -h 'https://es.example.local:9200' -u elastic \
  --kibana-url 'https://kibana.example.local:5601' \
  --ca-cert "$PWD/ca.crt" \
  -o "$BUNDLE_ROOT"
```

若兩者都未提供密碼檔或 API key，ES 與 Kibana 會各詢問一次密碼；輸入時不回顯。提示中的帳號來自各自的設定：ES 使用 `-u`，Kibana 使用 `KIBANA_USERNAME`，兩者互不自動帶入。排程或其他非互動執行必須改用權限 `600` 的密碼檔或 API key：

```bash
export KIBANA_USERNAME='elastic'
export KIBANA_PASSWORD_FILE='/run/secrets/kibana-password'
```

若同時採集 Logstash，將 `--services` 改為 `es,kibana,logstash`，並另提供
`--logstash-url` 及 `LOGSTASH_USERNAME`／`LOGSTASH_PASSWORD_FILE`。

本機 Host OS 證據可加入 `host`；多主機時複製 `collectors/ssh-hosts.conf.example`，填入每行 `host-id|ssh-user@hostname` 的清單：

```text
es-node-01|elkops@10.0.0.11
es-node-02|elkops@10.0.0.12
```

```bash
./collect.sh \
  --services es,host \
  -h 'https://es.example.local:9200' -u elastic \
  --ssh-hosts-file "$PWD/ssh-hosts.conf" \
  --ca-cert "$PWD/ca.crt" \
  -o "$BUNDLE_ROOT"
```

SSH 模組只使用既有 key／agent，不接收或保存 SSH 密碼。Host 模組目前不收完整 process argv、服務設定檔或日誌，避免把密碼與業務內容帶入採集包。

HTML 仍以 Elasticsearch 為主要診斷來源；若採集包包含 `kibana/`，分析階段會另外產生 Kibana 服務區塊：核心健康（`/api/status`）、Task Manager 健康（`/api/task_manager/_health`）與 Alerting 健康（`/api/alerting/_health`）會各自產生診斷卡，`/api/stats` 可解析數值則保存為 `INFO` measurements。報告版面會把 Elasticsearch 與 Kibana 分成獨立服務區塊，方便直接定位 Kibana 結果。`host/`、`logstash/` 目前仍是原始證據；HTML 「技術資訊」會列出採集包含的模組，分析指令不變。

Kibana stats 是單次觀測值，不會單獨升級健康等級；缺少、403 或無法解析時會顯示 `SKIPPED`，不會污染 Elasticsearch 結果。Task Manager／Alerting 的非 2xx、缺少必要欄位或格式錯誤會顯示 `UNKNOWN`，不得解讀成正常。

採集包中可能包含 index、node、IP、hostname、mapping 欄位名稱及選配的主機／服務中繼資料；外傳前依資料治理流程審閱與加密傳輸。部分 API 的 HTTP 400／403 可能是語意回應或權限限制，交由分析報告判讀。

完整取得選配強化資訊需 `read_ilm`、`monitor_snapshot`、cluster `monitor` 與 index
`view_index_metadata`。權限不足只會讓相關卡片顯示 `unknown`，不會中止其他資料採集與報告產生。

### 3.2 分析端產生報告

`BUNDLE_ROOT` 必須指向直接包含 `_manifest.json` 與 `elasticsearch/` 的採集包根目錄，不可指到 `elasticsearch/` 子目錄。

- 若在同一台機器、同一個 Terminal 接續操作：直接沿用 3.1 的 `BUNDLE_ROOT`，不要重新設定。
- 若已將採集包移到另一台分析機器：只需依實際位置重新設定一次：

```bash
export BUNDLE_ROOT='/收到的採集包絕對路徑'
```

確認路徑後產生報告：

```bash
test -f "$BUNDLE_ROOT/elasticsearch/version.json"

export REPORT_ROOT="$PWD/reports/$(basename "$BUNDLE_ROOT")"
mkdir -p "$REPORT_ROOT"

env -i PATH='/usr/bin:/bin' ./elk-diagnostics check \
  --from-bundle "$BUNDLE_ROOT" \
  --output html \
  --output-file "$REPORT_ROOT/check.html" \
  --metrics-output "$REPORT_ROOT/metrics.ndjson"
```

確認兩份輸出都存在：

```bash
test -s "$REPORT_ROOT/check.html" &&
test -s "$REPORT_ROOT/metrics.ndjson" &&
echo '離線分析產物：OK'
```

顯示 `離線分析產物：OK` 代表 HTML 與趨勢數值檔都存在且不是空檔；未顯示 `OK` 或出現錯誤即未通過，請先檢查前一步的分析輸出與 `REPORT_ROOT`。

同一採集包可再產生 JSON：

```bash
env -i PATH='/usr/bin:/bin' ./elk-diagnostics check \
  --from-bundle "$BUNDLE_ROOT" \
  --output json \
  --output-file "$REPORT_ROOT/check.json"
```

`env -i` 讓分析端不帶入 ES host、帳密或 CA；`--from-bundle` 全程不連線 ES。HTML 為離線單檔。

`metrics.ndjson` 每行是一筆帶 UTC 時間、`cluster_uuid`、node／診斷識別與單位的觀測值，適合後續匯入資料平台。它不包含連線 URL、帳密或採集包路徑；累積型 counter（如 GC、I/O、eviction）必須以前後差值判讀，不能把單次原始值視為當下壓力。

HTML 會在數值型診斷卡顯示「本次觀測值」；個別節點數值以節點名稱區分，叢集整體數值則標示為「叢集」。其中「累積值」仍需比較不同採集時間的 `metrics.ndjson`，HTML 不提供歷史趨勢圖。

## 4. 報告與結束碼

| code | 意義 |
|---:|---|
| 0 | 全部 pass／info，或只有 skipped |
| 1 | 含 warning |
| 2 | 含 critical |
| 3 | 含 unknown，且沒有 warning／critical |
| 10 | 參數或設定錯誤 |
| 11 | 連線、認證或採集包讀取失敗 |
| 20 | 工具或輸出錯誤 |

`1`／`2` 代表診斷結果，不代表報告產生失敗；先確認報告檔，再依卡片內容處理。

## 5. 能力邊界

- 現行診斷規則以 ES API 為主；Kibana bundle 會分析 `/api/status`、`/api/task_manager/_health`、`/api/alerting/_health`，`/api/stats` 僅保存為 `INFO` measurements。選配子採集器仍可透過 SSH 收集有限 Host OS 證據與 Logstash API 原始回應，尚未產生 Host／Logstash 診斷卡。
- CPU、I/O、GC、CCR lag、近期重啟與 indexing pressure 多為單次快照，需搭配 Monitoring 或時間序列判讀。
- 403／缺少權限會標示 `unknown` 或 `skipped`，不會當成正常。
- 採集包路線目前支援完整 `check`，不支援離線 `diagnose`。
- 工具不提供自動修復；所有修改由維運人員人工審核。

API 呼叫面請參閱交付包內的 [`API清單.md`](./API清單.md)。
