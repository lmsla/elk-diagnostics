# elk-diagnostics 前線工程師使用手冊

> 給前線工程師：先判斷情境，再照最短流程採集或產生報告。這份手冊保留 ELI5 的核心——先用白話說明「正在做什麼」，再給可直接執行的指令，最後說清楚不能推論什麼。

## 先記住三件事

1. **一次只選一條路線。** 不確定時，選 Route A。
2. **Basic Auth 與 API key 二選一。** 密碼不要放進指令、設定檔或 shell history。
3. **報告是唯讀診斷與證據整理，不是自動修復，也不保證直接給出根因。**

## 這個工具在做什麼？

把它想成兩個角色：

- `collect.sh` 是「量測員」：對指定服務送出唯讀 HTTP GET，保存回應並在壓縮前依選項遮蔽。
- `elk-diagnostics` 是「判讀員」：讀取即時回應或採集包，套用診斷規則，產生 HTML、JSON 或文字報告。

這是幫助理解的類比；實際邊界如下：工具不寫入 Elasticsearch，不執行修復，不讀取文件內容。採集包可能保存 index 名稱、node／hostname、IP、filesystem 與 mapping 欄位名稱，交付前仍要人工檢查。

## 30 秒選路線

| 現場情境 | 使用路線 | 入口 |
|---|---|---|
| 正式環境不允許執行未知二進位檔，或資料必須帶回指定分析環境 | **Route A：採集後離線分析** | `./collect.sh` → `check --from-bundle` |
| 已核准的分析機可以執行交付執行檔，且能連到 ES | **Route B：Live 直連** | `elk-diagnostics check` |
| 需要一併收集 Host、Kibana、Logstash 證據 | **Route A** | `./collect.sh --services ...` |
| 已知症狀，且分析機可直接連到 ES | **Route B** | `elk-diagnostics diagnose --symptom ...` |
| 目前不知道問題在哪裡 | 任一路線 | 先跑完整 `check` |

**不要混用路線。** Route A 的現場端只執行 `collect.sh`；Route B 的分析機直接執行 `elk-diagnostics`。如果沒有即時連線，`diagnose` 不能直接拿採集包執行；請先用 `check --from-bundle`。

## 共通安全規則

- 正式環境要驗證 TLS 憑證。自簽或私有 CA 使用 `--ca-cert`；`--insecure` 只限測試環境。
- Basic Auth 省略密碼參數，讓互動式終端安全詢問。自動化環境由秘密管理機制注入密碼。
- API key 放在權限為 `600` 的檔案，或由秘密管理機制注入環境變數；不要把實際 key 貼進指令。
- `403` 是權限或認證問題，不是「服務正常」。缺資料會形成 `unknown`／`skipped`，不能當成 `pass`。
- 單次執行是快照。高 CPU、RAM、I/O、heap 或累積計數不能單靠一次結果證明根因。
- 本流程交付 HTML／JSON／text／NDJSON；**沒有 PNG 匯出流程**。截圖只能當溝通輔助，不是正式診斷輸出。

## Route A：現場採集，帶回分析

> **採集前重要提醒：先決定資料遮蔽，再開始採集。**
>
> 把採集包想成要寄出的包裹：哪些文字要遮住，要在裝箱前決定。
>
> - IPv4 的前兩段每次都會固定遮蔽，例如 `10.99.1.123` 會變成 `xx.xx.1.123`。
> - 如果也不希望報告看到可識別的 index、data stream 或 backing index，請在採集指令中加入 `--redact-index-names`；採集完成後才加已經來不及。
> - 這個選項不會遮蔽 node name、hostname、mapping 欄位名稱或 pipeline／policy／snapshot 名稱；它不是完整匿名化。

### 1. 檢查交付包

在交付包目錄執行。checksum 不通過就停止，不要繼續採集。

```sh
cd /交付包實際路徑

if command -v sha256sum >/dev/null 2>&1; then
  sha256sum -c checksums/*.sha256
elif command -v shasum >/dev/null 2>&1; then
  shasum -a 256 -c checksums/*.sha256
else
  echo '找不到 sha256sum 或 shasum，無法驗證交付包'
  exit 2
fi

command -v curl >/dev/null 2>&1 && \
test -x ./collect.sh && \
echo '採集前置檢查：OK'
```

### 2. 建立預期節點清單

這份清單只寫 Elasticsearch 的 `node.name`，用來找出「採集開始前就已離線」的節點。IP、角色與其他資訊由 API 取得。

```sh
if [ ! -f expected-es-nodes.txt ]; then
  cp expected-es-nodes.txt.example expected-es-nodes.txt
fi

# 請用核准的編輯器，把範例名稱改成實際 node.name；每行一個。
test -s ./expected-es-nodes.txt && \
echo '預期 ES 節點清單：OK'
```

檔案內容範例（請把名稱全部換成現場實際的 `node.name`）：

```text
es-node-01
es-node-02
es-node-03
```

如果拿不到可靠的 `node.name` 清單，可以省略這一步；報告會標示只能確認目前在線節點。

### 3. Basic Auth 採集（私有／自簽 CA）

這是最常用的互動式範例。執行後輸入密碼；密碼不會出現在指令列。

```sh
cd /交付包實際路徑
ES_URL='https://es.example.local:9200'
ES_USER='elastic'
CA_CERT='/實際憑證路徑/ca.crt'
BUNDLE_ROOT="$PWD/bundle-$(date +%Y%m%d-%H%M%S)"

test -r "$CA_CERT" && \
test -s "$PWD/expected-es-nodes.txt" || exit 2

(
  unset ES_PASSWORD_FILE ES_PASSWORD ES_API_KEY
  ./collect.sh \
    --services es \
    --host "$ES_URL" \
    --username "$ES_USER" \
    --ca-cert "$CA_CERT" \
    --expected-es-nodes-file "$PWD/expected-es-nodes.txt" \
    --output "$BUNDLE_ROOT"
)
```

公有 CA 環境：移除 `CA_CERT` 變數、憑證檢查，以及指令中的 `--ca-cert "$CA_CERT"`。

### 4. API key 採集

Basic Auth 與 API key 是替代方案，不要同時設定。以下使用權限為 `600` 的 key 檔案；若已由秘密管理機制提供 `ES_API_KEY`，可保留該環境變數並略過讀檔分支。

```sh
cd /交付包實際路徑
ES_URL='https://es.example.local:9200'
API_KEY_FILE='/安全目錄/elk-api-key'
CA_CERT='/實際憑證路徑/ca.crt'
BUNDLE_ROOT="$PWD/bundle-$(date +%Y%m%d-%H%M%S)"

test -r "$CA_CERT" && \
test -s "$PWD/expected-es-nodes.txt" || exit 2

(
  unset ES_PASSWORD_FILE ES_PASSWORD
  if [ -n "${ES_API_KEY:-}" ]; then
    export ES_API_KEY
  else
    test -s "$API_KEY_FILE" || exit 2
    ES_API_KEY="$(cat "$API_KEY_FILE")"
    export ES_API_KEY
  fi

  ./collect.sh \
    --services es \
    --host "$ES_URL" \
    --ca-cert "$CA_CERT" \
    --expected-es-nodes-file "$PWD/expected-es-nodes.txt" \
    --output "$BUNDLE_ROOT"
)
```

API key 版本不要加 `--username`。公有 CA 環境同樣移除 `CA_CERT` 與 `--ca-cert`。

### 5. 同時採集 Kibana 與 Logstash

預設只採集 Elasticsearch。需要把 Kibana、Logstash 一起放進同一份 Bundle 時，不要只複製最後的 `./collect.sh`；先把三份清單準備好，再執行完整區塊。

#### 5.1 先建立並填寫清單

在交付包目錄執行一次：

```sh
cd /交付包實際路徑

if [ ! -f expected-es-nodes.txt ]; then
  cp expected-es-nodes.txt.example expected-es-nodes.txt
fi
if [ ! -f kibana-instances.conf ]; then
  cp kibana-instances.conf.example kibana-instances.conf
fi
if [ ! -f logstash-instances.conf ]; then
  cp logstash-instances.conf.example logstash-instances.conf
fi
```

用文字編輯器把範例內容換成現場值：

- `expected-es-nodes.txt`：每行一個正確的 ES `node.name`，不填 IP 或 role。
- `kibana-instances.conf`：每行 `instance-label|Kibana URL`。
- `logstash-instances.conf`：每行 `instance-label|Logstash Node API URL`。

`expected-es-nodes.txt` 的內容範例（請換成現場實際 `node.name`）：

```text
es-node-01
es-node-02
es-node-03
```

例如：

```text
# kibana-instances.conf
kibana-01|https://kibana-01.example.local:5601
kibana-02|https://kibana-02.example.local:5601

# logstash-instances.conf
logstash-01|https://logstash-01.example.local:9600
logstash-02|https://logstash-02.example.local:9600
```

`instance-label` 是使用者自訂且不可重複的標籤；URL 才是實際連線目標。這個多 instance 範例使用清單，因此不要再同時設定 `--kibana-url`／`--logstash-url`；單一 instance 才改用 URL 參數。

#### 5.2 填寫參數並執行

以下是 Basic Auth 範例。把它想成三把不同的門鎖：ES、Kibana、Logstash 各自設定帳號；執行時會互動詢問未提供密碼檔的服務密碼。API key 是另一條認證路徑，不要與同一服務的 Basic Auth 同時設定。

| 參數／檔案 | 要填什麼 |
|---|---|
| `ES_URL`／`ES_USER` | 實際 ES URL 與具備唯讀權限的帳號。 |
| `CA_CERT` | 自簽／私有 CA 的實際路徑；公有 CA 移除此變數、檢查與 `--ca-cert`。 |
| `KIBANA_USER`／`LOGSTASH_USER` | 對應服務帳號；未使用 Basic Auth 時留空。 |
| 三份清單 | 已填入現場實際節點／instance；檔案必須可讀。 |
| `BUNDLE_ROOT` | 指令自動以時間建立的新目錄，不要改成舊採集包。 |

```sh
cd /交付包實際路徑
ES_URL='https://es.example.local:9200'
ES_USER='elastic'
CA_CERT='/實際憑證路徑/ca.crt'
KIBANA_USER='elastic'
LOGSTASH_USER=''
BUNDLE_ROOT="$PWD/bundle-elk-$(date +%Y%m%d-%H%M%S)"

test -r "$CA_CERT" && \
test -s "$PWD/expected-es-nodes.txt" && \
test -s "$PWD/kibana-instances.conf" && \
test -s "$PWD/logstash-instances.conf" && \
test -d "$PWD/collectors" || exit 2

(
  export KIBANA_USERNAME="$KIBANA_USER"
  export LOGSTASH_USERNAME="$LOGSTASH_USER"
  unset ES_PASSWORD_FILE ES_PASSWORD ES_API_KEY
  unset KIBANA_PASSWORD_FILE KIBANA_API_KEY KIBANA_CA_CERT
  unset LOGSTASH_PASSWORD_FILE LOGSTASH_API_KEY LOGSTASH_CA_CERT

  ./collect.sh \
    --services es,kibana,logstash \
    --host "$ES_URL" \
    --username "$ES_USER" \
    --kibana-list "$PWD/kibana-instances.conf" \
    --logstash-list "$PWD/logstash-instances.conf" \
    --ca-cert "$CA_CERT" \
    --expected-es-nodes-file "$PWD/expected-es-nodes.txt" \
    --output "$BUNDLE_ROOT"
)
```

公有 CA 環境移除 `CA_CERT`、憑證檢查與 `--ca-cert`。若改用 API key，請由交付人員提供對應的秘密注入方式；不要把 key 貼進指令或設定檔。

採集腳本會逐一列出每個 label 與 URL 的結果，最後輸出 ES、Kibana、Logstash 摘要。某個目標出現 `connection failed` 時，要看該目標的 `_status.txt`；它可能是 URL、網路、TLS、帳號或權限問題，不能只憑這行字判定 instance 已離線。

### 6. 確認採集完成

```sh
test -s "$BUNDLE_ROOT/elasticsearch/version.json" && \
test -s "$BUNDLE_ROOT/_manifest.json" && \
test -s "$BUNDLE_ROOT/_status.txt" && \
test -s "$BUNDLE_ROOT.tar.gz" && \
echo '採集包與壓縮檔：OK'

sed -n '1,200p' "$BUNDLE_ROOT/_status.txt"
```

交付前仍要依客戶資料政策確認 Bundle 可以傳送；遮蔽選項只能降低部分識別性，不能取代人工審閱。

### 7. 在分析機離線產生報告

分析機不需要連到 ES，也不需要 ES 帳密或 CA。先解壓，再把 `--from-bundle` 指向**包含 `_manifest.json` 的目錄**，不是 `.tar.gz` 檔案本身。

```sh
cd /分析端實際路徑
tar -xzf /交付包路徑/bundle-<時間戳>.tar.gz

BUNDLE_ROOT='/解壓後/包含_manifest.json的採集目錄'
TOOL_BIN="$PWD/elk-diagnostics-linux-amd64"
REPORT_ROOT="$PWD/reports/$(basename "$BUNDLE_ROOT")"

test -x "$TOOL_BIN" && \
test -s "$BUNDLE_ROOT/_manifest.json" && \
test -s "$BUNDLE_ROOT/_status.txt" || exit 2

mkdir -p "$REPORT_ROOT"
"$TOOL_BIN" check \
  --from-bundle "$BUNDLE_ROOT" \
  --output html \
  --output-file "$REPORT_ROOT/check.html" \
  --metrics-output "$REPORT_ROOT/metrics.ndjson"

test -s "$REPORT_ROOT/check.html" && \
test -s "$REPORT_ROOT/metrics.ndjson" && \
echo 'HTML 報告與趨勢資料：OK'
```

`linux-arm64` 交付包要使用對應的 ARM64 執行檔。這個步驟只做分析與輸出，不會回寫現場叢集。

## Route B：分析機 Live 直連

### Basic Auth

只在已核准的分析機使用。執行後由互動式終端詢問密碼。

```sh
cd /交付包實際路徑
ES_URL='https://es.example.local:9200'
ES_USER='elastic'
CA_CERT='/實際憑證路徑/ca.crt'
TOOL_BIN="$PWD/elk-diagnostics-linux-amd64"
REPORT_ROOT="$PWD/reports/live-$(date +%Y%m%d-%H%M%S)"

test -x "$TOOL_BIN" && test -r "$CA_CERT" || exit 2

(
  unset ELK_DIAGNOSTICS_HOSTS ELK_DIAGNOSTICS_AUTH_TYPE
  unset ELK_DIAGNOSTICS_USERNAME ELK_DIAGNOSTICS_PASSWORD
  unset ELK_DIAGNOSTICS_CA_CERT ELK_DIAGNOSTICS_API_KEY ELK_DIAGNOSTICS_TOKEN

  mkdir -p "$REPORT_ROOT"
  "$TOOL_BIN" check \
    --host "$ES_URL" \
    --username "$ES_USER" \
    --ca-cert "$CA_CERT" \
    --output html \
    --output-file "$REPORT_ROOT/check.html" \
    --metrics-output "$REPORT_ROOT/metrics.ndjson"
)
```

公有 CA 環境移除 `CA_CERT`、憑證檢查與 `--ca-cert`。不要使用已棄用的 `--password`。

### API key

```sh
cd /交付包實際路徑
ES_URL='https://es.example.local:9200'
TOOL_BIN="$PWD/elk-diagnostics-linux-amd64"
REPORT_ROOT="$PWD/reports/live-$(date +%Y%m%d-%H%M%S)"
API_KEY_FILE='/安全目錄/elk-api-key'
CA_CERT='/實際憑證路徑/ca.crt'

(
  unset ELK_DIAGNOSTICS_AUTH_TYPE ELK_DIAGNOSTICS_USERNAME ELK_DIAGNOSTICS_PASSWORD
  unset ELK_DIAGNOSTICS_TOKEN
  test -s "$API_KEY_FILE" || exit 2
  ELK_DIAGNOSTICS_API_KEY="$(cat "$API_KEY_FILE")"
  export ELK_DIAGNOSTICS_API_KEY

  test -x "$TOOL_BIN" && test -r "$CA_CERT" || exit 2
  mkdir -p "$REPORT_ROOT"
  "$TOOL_BIN" check \
    --host "$ES_URL" \
    --ca-cert "$CA_CERT" \
    --output html \
    --output-file "$REPORT_ROOT/check.html" \
    --metrics-output "$REPORT_ROOT/metrics.ndjson"
)
```

### 已知症狀的聚焦排查

`diagnose` 是 Live 直連用的聚焦診斷，不是採集包入口。先有明確症狀才使用；不知道問題在哪裡就跑完整 `check`。

| 症狀 | 何時使用 |
|---|---|
| `red-cluster` | 叢集為 red／yellow，或有未分配 shard |
| `write-bottleneck` | 寫入變慢、write queue 或 rejected requests 可疑 |
| `high-heap` | JVM heap 壓力或 circuit breaker 可疑 |
| `ingest-lag` | ingest pipeline、佇列或寫入延遲可疑 |
| `ilm-stuck` | ILM 長時間停滯或出現 ERROR |

```sh
SYMPTOM='write-bottleneck'
"$TOOL_BIN" diagnose \
  --symptom "$SYMPTOM" \
  --host "$ES_URL" \
  --username "$ES_USER" \
  --ca-cert "$CA_CERT" \
  --output html \
  --output-file "$REPORT_ROOT/$SYMPTOM.html"
```

若改用 API key，省略 `--username`，依前一節注入 `ELK_DIAGNOSTICS_API_KEY`。本手冊只使用目前交付執行檔可確認的旗標；若交付包內 `--help` 與文件不同，以實際執行檔為準，並回報 `version` 與 `--help` 輸出。

## 怎麼看結果？

先看報告頂端的 `overall_status`，再沿著 findings、evidence 與 extra guidance 往下看。

| 狀態 | 白話意思 | 下一步 |
|---|---|---|
| `pass` | 這次取得的資料沒有觸發該規則 | 不代表所有歷史或未採集面向都正常 |
| `warning` | 找到需要關注的訊號 | 依報告 guidance 補查或觀察趨勢 |
| `critical` | 找到嚴重訊號 | 依證據與變更流程處理，不要直接把建議當修復指令 |
| `unknown` | 資料不足、權限不足、API 失敗或回應不完整 | 先補權限／連線／採集，再判斷 |
| `skipped` | 此項不適用或版本不支援 | 不把 skipped 當成 pass |

### 結束碼

`check`／`diagnose` 可供排程或 CI 使用：

| code | 意義 |
|---:|---|
| `0` | 全 pass／info，或只有 skipped |
| `1` | 最高為 warning |
| `2` | 存在 critical |
| `3` | 存在 unknown，且沒有 critical／warning |
| `10` | 設定錯誤 |
| `11` | 所有 host 連線／認證失敗 |
| `20` | 工具或輸出錯誤 |

`1`／`2` 是診斷結果，不等於 HTML 產生失敗；要另外確認輸出檔是否存在且非空。

## 這些情況先停下來

| 現象 | 不要做什麼 | 正確處理 |
|---|---|---|
| checksum 失敗 | 不要繼續執行 | 重新取得完整交付包，通知交付者 |
| 找不到 `curl` 或 `collect.sh` 不可執行 | 不要自行改權限或替換腳本 | 回報作業系統與前置檢查結果 |
| TLS 憑證錯誤 | 不要在正式環境加 `--insecure` | 取得正確 CA 憑證並用 `--ca-cert` |
| `403`／認證失敗 | 不要把結果當成健康 | 確認帳號、API key 權限與服務端政策 |
| `unknown` 或 API response partial | 不要自行補成正常 | 補採集或補權限；保留 unknown |
| ES `< 8.4` | 不要宣稱完整支援 | 依報告的版本提示解讀；部分項目會 skipped／帶 warning |
| Bundle 含仍可識別的業務相關名稱 | 不要直接外傳 | 確認已使用 `--redact-index-names`；node name、hostname、mapping 欄位與 pipeline／policy 名稱仍需依資料政策人工審閱 |

- [ ] 只選一種認證方式，沒有把密碼／API key 寫進指令或檔案交付物。

### Route B

- [ ] 使用正確 CPU 架構的執行檔，checksum 通過。
- [ ] TLS 憑證驗證方式已確認。
- [ ] 已產出非空的 `check.html`；需要趨勢資料時也確認 `metrics.ndjson`。
- [ ] 已記錄工具版本、目標 URL、執行時間與結束碼，但沒有記錄秘密。

## 最後的教回測試

如果只能把流程交給下一位同事三句話：

> 不能在客戶環境跑未知執行檔，就用 Route A，只跑 `collect.sh`，再帶回分析。
>
> 可以在核准分析機直連 ES，才用 Route B；已知症狀才用 `diagnose`。
>
> 結果是證據與判讀，不是修復命令；`unknown` 代表資料不夠，不代表正常。
