# 診斷卡分類與門檻盤點

> 盤點基準：`elk-diagnostics` 1.0.1 baseline（2026-09-16）
>
> 目的：把目前報告會產出的診斷卡逐條列出，區分「Elastic 直接判定」、「官方建議值」與「工具自行設定的預警 heuristic」，供後續逐條確認。本文是盤點文件，不代表所有門檻都已獲得最終產品核准。

## 1. 先看分類原則

目前的診斷卡至少要沿兩個維度閱讀，不能把「資料來源」誤當成「門檻來源」：

| 分類 | 意義 |
|---|---|
| `health_report` | 直接讀 Elasticsearch `_health_report` 的 indicator；`green/yellow/red` 是 ES 回傳的狀態，不是本工具自行計算的數值門檻。 |
| `raw_api / state` | 從 API 回傳的狀態、設定或事件直接判斷，例如 `failed`、`blocked=true`、`tripped>0`。事件本身是真實觀測值，但「要標成 warning 或 critical」可能仍是工具政策。 |
| `raw_api / numeric` | 工具從 API 數值自行比較，例如 JVM、CPU、queue、時間、比例、shard 大小。這些才需要逐條確認門檻來源。 |
| `observation` | 有數值但只適合呈現趨勢或單次觀察，不能由單次快照直接宣稱故障。 |
| `service` | Kibana／Logstash 的服務可用性、健康 API 與 pipeline 觀測；服務未採集時不會加入對應診斷卡。 |

### 門檻來源標籤

| 標籤 | 定義 |
|---|---|
| `官方機制` | Elastic 產品內建的限制、拒絕條件或 API 狀態，例如 disk watermark、shard limit、indexing pressure 的拒絕上限。 |
| `官方建議` | Elastic 文件提供的建議值或經驗範圍，不是統一的 PASS/WARNING/CRITICAL 規格。 |
| `工具 heuristic` | 本專案為單次快照設計的預警門檻；可由 `--rules` 覆寫，不能對客戶宣稱是 Elastic 強制標準。 |
| `狀態直證` | API 已直接回傳異常狀態或設定事實；嚴重度映射仍需看本專案規則。 |
| `無數值門檻` | 只列出資訊、配置或狀態，不用數值切 PASS/WARNING/CRITICAL。 |

`rules/default.yaml` 的目前預設值與註解見 [rules/default.yaml](../../../rules/default.yaml)。A/B 類與 C 類連續型指標的設計邊界見 [規則規格.md](./規則規格.md)。

## 2. `_health_report` 直接判定卡（A/B 類）

這些卡片直接轉述 ES indicator：`green → pass`、`yellow → warning`、`red → critical`、其他狀態 → `unknown`。它們不是本工具用一組自訂數字重新計算；若 indicator 內容有數值，仍應以 ES 回傳的 diagnosis/context 為準。

| 診斷卡 ID | 顯示名稱 | 目前判定依據 | 門檻來源 | 快照限制 | 確認 |
|---|---|---|---|---|---|
| `cluster_health` | 叢集健康／未分配 shard | `shards_availability` status | `狀態直證` | 只代表採集當下 | [ ] |
| `disk` | 磁碟容量／watermark | `disk` status 與 ES diagnosis | `官方機制` | 以採集時設定與回應為準 | [ ] |
| `shards_capacity` | Shard 容量上限 | `shards_capacity` status；容量數值另由 ES 設定計算 | `官方機制` + 報告呈現規則 | 上限不是 sizing 建議 | [ ] |
| `snapshot_repository` | Snapshot repository 完整性 | `repository_integrity` status | `狀態直證` | 不等於已完成還原演練 | [ ] |
| `slm` | SLM 快照政策 | `slm` status | `狀態直證` | 需搭配 snapshot freshness | [ ] |
| `master_stability` | Master 穩定性 | `master_is_stable` status | `狀態直證` | 不能取代事件時間序列 | [ ] |
| `data_stream_lifecycle` | Data stream 生命週期／tier | `data_stream_lifecycle` status | `狀態直證` | 需對照實際 ILM／DSL 政策 | [ ] |

## 3. 目前有明確數值比較的卡片

下表是目前最需要逐條確認「數值多少算 pass、何時 warning、何時 critical」的範圍。除非標示為 `官方機制`，否則不應把目前數字說成 Elastic 官方硬性門檻。

| 診斷卡 ID | 目前內建判定 | 門檻來源 | 單次快照限制 | 確認 |
|---|---|---|---|---|
| `jvm_memory_pressure` | JVM old pool `≥85%` warning；`≥95%` critical | `85%` 為 `官方建議`；`95%` 接近 ES circuit breaker 壓力點；嚴重度映射為 `工具 heuristic` | 持續性與 GC 需時間序列 | [ ] |
| `high_cpu` | CPU `≥85%` warning，無本卡自訂 critical | `85%` 是保守的 `工具 heuristic`；官方通常要求持續高於 `95%` 才調查 | CPU 是瞬時值 | [ ] |
| `task_backlog` | thread pool queue `≥50` warning | `工具 heuristic` | queue 是瞬時值 | [ ] |
| `mapping_explosion` | 欄位數達實際／預設上限的 `80%` warning；達上限 critical | `1000` 是 ES 設定的官方預設；`80%` 是 `工具 heuristic` | 目前可能使用 fallback 上限，應優先讀實際 index 設定 | [ ] |
| `ingest_pipeline_errors` | 累積失敗率 `>10%` warning | Elastic troubleshooting 有 `>10%` 的查詢範例，但不是產品硬限制；標為 `官方建議／工具 heuristic` | `count/failed` 是自節點啟動累積值 | [ ] |
| `hot_spotting` | 同類節點指標至少 `50%`，且高於中位數 `30` 個百分點 → info | `工具 heuristic` | 單次差距不能證明持續 hot spotting | [ ] |
| `node_file_descriptor_pressure` | open/max `≥80%` warning；`≥90%` critical | `工具 heuristic`；Elastic 的官方要求是 `nofile ≥65,535`，不是 80/90% | 需確認實際上限與持續成長 | [ ] |
| `node_cgroup_memory_pressure` | 有限 cgroup 下 usage/limit `≥90%` warning | `工具 heuristic` | usage 含可回收 file cache，不能單次升 critical | [ ] |
| `cluster_pending_tasks` | queue `≥30` 秒 warning；`≥300` 秒 critical | `工具 heuristic` | 需對照 maintenance window 與 task source | [ ] |
| `long_running_tasks` | task 執行 `≥300` 秒 warning | `工具 heuristic` | 長任務可能是合法批次工作 | [ ] |
| `shard_sizing` | 單一 primary shard `≥50 GiB` 列／卡 warning；`≤1 GiB` 且數量 `≥100` 為整卡聚合 warning，個別小 shard 列不繼承 warning；本卡無 critical | `10–50 GiB` 是 Elastic sizing guidance；小 shard 大小與數量是 `工具 heuristic` | 需依 workload、文件數與 recovery 目標校正 | [ ] |
| `snapshot_freshness` | 最近成功 snapshot `≥48` 小時 warning；`≥168` 小時 critical | `工具 heuristic`，代表預設 RPO | 必須依客戶正式備份政策覆寫 | [ ] |
| `tls_certificate_expiry` | `≤100` 天 warning；已過期的 identity certificate critical | 到期是 `狀態直證`；100 天提前量是 `工具 heuristic` | `/_ssl/certificates` 只涵蓋回應節點 | [ ] |
| `license_expiry` | `≤100` 天 warning；`expired/invalid` critical | 過期／invalid 是 `狀態直證`；100 天提前量是 `工具 heuristic` | 需確認 license 是否為正式續約流程 | [ ] |
| `indexing_pressure` | 相對拒絕上限 `≥80%` warning；`≥95%` critical | limit 與 replica `1.5×limit` 是 `官方機制`；80/95 分界是 `工具 heuristic` | 單次值不能證明持續背壓 | [ ] |
| `ccr_health` | global checkpoint lag `≥10,000` warning；fatal/read exception critical | exception 是 `狀態直證`；10,000 是 `工具 heuristic` | lag 與 failed counter 需趨勢佐證 | [ ] |
| `recent_node_restart` | uptime `<60` 分鐘 warning | `工具 heuristic` | 只能證明近期啟動，不能推斷 crash | [ ] |
| `master_stability_context` | 0 個 master-eligible critical；1 個或偶數 warning；奇數且 `≥3` pass | 奇數／至少 3 個屬拓樸建議；細部分級是 `工具 heuristic` | 結構風險不等於當下已故障 | [ ] |

|---|---|---|---|---|
| `rejected_requests` | search/write `rejected>0` → warning | 事件是 `狀態直證`；warning 映射是 `工具 heuristic` | rejected 是累積值；需雙次採集看差值 | [ ] |
| `circuit_breaker` | breaker `tripped>0` → warning | 事件是 `狀態直證`；warning 映射是 `工具 heuristic` | tripped 是累積值 | [ ] |

| `node_swap_usage` | swap used `>0` → warning | Elastic 明確建議避免 swapping；嚴重度映射是 `工具 heuristic` | 只代表採集當下／目前累積使用量 | [ ] |
| `node_memory_lock` | `mlockall=false` 且 swap total `>0` → warning | `狀態直證` + `工具 heuristic` | mlockall=false 單獨不代表故障 | [ ] |

## 7. 不要和診斷卡混在一起的報表內容

以下是報告的觀測／摘要區塊，不是獨立診斷卡，不應拿來和上表的 PASS/WARNING/CRITICAL 混為一談：

- **目前叢集狀態摘要**：單次採集快照，整理節點、服務、磁碟、shard 與核心服務現況。
- **Node Context 節點概況**：逐節點 CPU、OS RAM、JVM heap、磁碟、Swap、FD 與角色；數值本身不必然代表診斷卡已判定異常。
- **磁碟容量摘要**：呈現各節點已用／可用／總容量；實際 watermark 異常仍以 `disk` health indicator 為準。
- **Shard 容量摘要**：呈現目前使用量與 ES shard limit；容量數字不是「健康分數」，也不是官方 sizing 建議。
- **本次觀測值表格**：累積 counter 必須標示為累積值，不能直接解讀成持續故障。

## 9. 逐條確認順序

每張卡確認時，依下列順序填寫或補充本文件：

- [ ] 這張卡的資料來源與 API response 欄位已確認。
- [ ] 明確區分官方硬限制、官方建議、工具 heuristic 或狀態直證。
- [ ] 已寫出 pass／warning／critical 的實際條件；若沒有數值門檻，明確寫「無數值門檻」。
- [ ] 已標示單次快照、累積 counter、權限不足與版本不適用等限制。
- [ ] 已確認報告文案不會把工具 heuristic 說成 Elastic 官方標準。
- [ ] 已補上至少一個邊界測試案例，並確認 HTML／JSON／CLI 三種輸出一致。

## 11. 數值判定版面優化 checklist

以下 checklist 追蹤診斷卡是否已套用「目前值／上限／比例／判定」的精簡版面；未列入本輪的卡片維持原有觀測值或狀態呈現。

### JVM 記憶體壓力（`jvm_memory_pressure`）

- [x] 以一個節點一列呈現 Old pool 已用、上限、壓力與判定。
- [x] 顯示通過／警告／嚴重門檻與目前最高值。
- [x] 標示「官方建議 + 工具預警門檻」及單次快照限制。
- [x] 保留 JSON 結構化 `numeric_judgment`，不從 findings 文字解析。

### File descriptor 使用率（`node_file_descriptor_pressure`）

- [x] 以一個節點一列呈現 FD 已用、上限、使用率與判定。
- [x] 顯示 80%／90% 工具門檻，缺值列為無法判定。
- [x] 標示工具 heuristic 與單次快照限制。
