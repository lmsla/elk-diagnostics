# 症狀診斷規格 — 症狀診斷樹

**實作位置**：`cmd/diagnose.go`（症狀註冊與調度）＋ 各 analyzer。

`diagnose --symptom <x>` 不重跑全量，而是執行該症狀的**診斷樹**：一組依序、有因果關聯的診斷項，最後給出「症狀是否成立」的聚焦結論（報告格式見 診斷報告規格 §7）。

## 1. 症狀註冊表

| symptom | 對應診斷項（依序） | 聚焦結論 |
|---|---|---|
| `red-cluster` | #1 cluster_health → #2 unassigned_shards → #19/#20 allocation blocked → #3 watermark | 叢集為何 red/yellow，未分配 shard 的根因 |
| `write-bottleneck` | #16 因果鏈（CPU↓ → write queue↑ → allocated_processors↓）→ #6 rejected → #9 hot_threads | 寫入瓶頸是否來自 allocated_processors 過低（見 寫入瓶頸規格） |
| `high-heap` | #7 jvm_pressure → #8 circuit_breaker → #6 rejected | heap 壓力來源與連帶影響 |
| `ingest-lag` | #13 ingest_pipeline → #12 task_backlog → #6 rejected(write) → #3 watermark | 攝取延遲卡在 pipeline / 佇列 / 寫入哪一環 |
| `ilm-stuck` | #5 ilm（status + explain ERROR）→ #3 watermark → #10 shards_capacity | ILM 停滯是服務停用、step ERROR、或被資源/磁碟卡住 |

## 2. 診斷樹執行規則

1. 依序執行樹中各項，每項仍產出標準 `DiagnosticResult`。
2. **因果排序**：報告依樹的順序呈現，讓使用者沿因果鏈讀（非依 category 分組）。
3. **聚焦結論**：頂層 `overall_status` 表「該症狀是否成立」——
   - 樹中關鍵環節 confirmed → 症狀**成立**（指出根因環節）。
   - 僅部分環節 suspected → **疑似**，列出已成立/未成立環節，不妄下結論。
   - 關鍵環節皆 normal → 症狀**未由此樹解釋**，建議改跑 `check` 或其他症狀。
4. `--index` / `--interval` 等 flag 傳遞給樹中需要的診斷項（如 write-bottleneck 的雙取樣）。

## 3. 反向觸發（check → 建議 diagnose）

`check` 巡檢時若偵測到某症狀的特徵組合，於報告中主動提示對應 `diagnose`。例：
- 偵測「CPU 低 + write queue 積壓 + allocated_processors 偏低」→ 提示 `diagnose --symptom write-bottleneck`。
- 偵測「ILM ERROR」→ 提示 `diagnose --symptom ilm-stuck`。

## 4. 擴充方式

新增症狀＝在註冊表加一列（symptom → 診斷項序列 + 聚焦結論規則），複用既有 analyzer，不需新增診斷邏輯。新症狀若需新的診斷項，先補對應診斷規格再註冊。

## 5. 邊界

- 症狀樹只**重組既有診斷項的執行與呈現**，不引入新的判斷邏輯（write-bottleneck 的因果鏈邏輯在其專屬規格/analyzer）。
- 時間序列類環節（如 master 穩定性）在樹中一樣標「需持續觀察」，不臆測。

`tested_versions`: 調度層與 ES 版本無關；各環節沿用對應診斷。
