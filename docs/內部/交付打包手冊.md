# 內部交付打包手冊

本手冊供內部同事從已確認的 Git commit 準備交付給使用者的檔案。打包不等於功能驗證；必須先完成產物同步與測試。

## 1. 打包前提

- 從 repo 根目錄執行。
- 使用已確認的 `main` commit，且工作區必須乾淨。
- 已安裝 Go；首次產生 SBOM 時需連線下載固定版本的 `cyclonedx-gomod`。
- 不得把密碼、`config.yaml`、私鑰、測試憑證、採集包或未核准報告放入交付包。

確認版本與工作區：

```bash
git status --short --branch
git log -1 --oneline
```

若 `git status --short` 有輸出，先確認、測試並提交變更，不要直接打包。

## 2. 標準打包流程

依序執行：

```bash
make generate
git diff --exit-code -- collect.sh docs/交付/API清單.md
go test ./...
go vet ./...
make clean
make dist
```

判讀：

- `make generate`：依目前程式重新產生 `collect.sh` 與 API 清單。
- `git diff --exit-code`：確認產物沒有落後原始碼；若失敗，先審閱、提交，再重新開始。
- `go test`、`go vet`：確認程式與靜態檢查通過。
- `make clean`：移除舊 `dist/`，避免混入前一次打包檔案。
- `make dist`：建立 Linux amd64／arm64 binary、文件、checksum 與 SBOM。

`make dist` 可以單獨執行，但不會自動執行前三項檢查，因此內部交付不得省略上述順序。

注意：`make clean` 也會刪除 repo 根目錄的本機 `elk-diagnostics` binary，而 `make dist` 只建立 Linux 交付版本。若打包後仍要在 macOS 繼續測試，請重新建立本機版本：

```bash
make build
./elk-diagnostics version
```

## 3. `dist/` 候選產物

`make dist` 會把兩條路線可能使用的產物集中在 `dist/`。`dist/` 不是可直接整包交付的目錄；必須依 Route A／B 挑選。

| 檔案 | 用途 |
|---|---|
| `elk-diagnostics-linux-amd64` | Linux x86_64 分析端 binary |
| `elk-diagnostics-linux-arm64` | Linux ARM64 分析端 binary |
| `collect.sh` | Route A 使用者端採集腳本 |
| `collectors/` | Route A 選配 Host／Kibana／Logstash 子採集器 |
| `expected-es-nodes.txt.example` | 預期 ES `node.name` 清單範本；使用者填寫後另存為 `expected-es-nodes.txt` |
| `kibana-instances.conf.example` | 多 Kibana instance 清單範本；使用者依現場 URL 另存為 `kibana-instances.conf` |
| `logstash-instances.conf.example` | 多 Logstash instance 清單範本；使用者依現場 URL 另存為 `logstash-instances.conf` |
| `API清單.md` | API 與權限審查 |
| `使用手冊.md` | 路線選擇入口；不放任何共用參數區塊 |
| `路線A-採集操作手冊.md` | Route A 使用者端 Shell 採集操作；不含 binary 或分析指令 |
| `路線B-直連操作手冊.md` | Route B 執行檔、直連參數與報告產生操作 |
| `sbom.cdx.json` | `elk-diagnostics` binary 的 Go module 成分表 |
| `*.sha256` | 對應檔案的完整性校驗值 |

`rules/default.yaml` 已在編譯時內嵌 binary，不需另外交付。使用者自訂門檻時，才另行提供經審閱的 `custom.yaml` 並使用 `--rules custom.yaml`。

## 4. Route A／Route B 交付範圍

### Route B：Live 直連

使用者端會執行 binary，交付下列檔案：

| 必要性 | 檔案 |
|---|---|
| 必要 | 符合使用者端架構的 `elk-diagnostics-linux-*` |
| 必要 | 該 binary 的 `.sha256` |
| 必要 | `API清單.md`、`API清單.md.sha256` |
| 必要 | `使用手冊.md`、`使用手冊.md.sha256` |
| 必要 | `路線B-直連操作手冊.md`、其 checksum |
| 依資安要求 | `sbom.cdx.json`、`sbom.cdx.json.sha256` |
| 選配 | `expected-es-nodes.txt.example`、其 checksum；使用者依現場拓撲另存為 `expected-es-nodes.txt` |
| 選配 | `config.yaml.example` |

若使用者採用設定檔，另附 `config.yaml.example` 作為範本；目前 `make dist` 不會自動複製此檔。不得預先填入帳密、API key 或正式憑證私鑰。

### Route A：採集包

使用者端只執行 Shell 採集腳本，交付下列檔案：

| 必要性 | 檔案 |
|---|---|
| 必要 | `collect.sh`、`collect.sh.sha256` |
| 選配 | `expected-es-nodes.txt.example`、其 checksum；使用者依現場拓撲另存為 `expected-es-nodes.txt` |
| 使用多 instance | `kibana-instances.conf.example`、`logstash-instances.conf.example` 及其 checksum；使用者填寫後另存為實際清單 |
| 必要 | `API清單.md`、`API清單.md.sha256` |
| 必要 | `使用手冊.md`、`使用手冊.md.sha256` |
| 必要 | `路線A-採集操作手冊.md`、其 checksum |
| 使用 `--services` 時必要 | `collectors/` 與其 `*.sha256` |

Route A 使用者端**不交付** binary、binary checksum、SBOM 或 `config.yaml.example`。分析端內部保留 binary 與 SBOM，用來離線分析使用者回傳的採集包。

`expected-es-nodes.txt` 不直接放入 `dist/`：它必須由使用者依現場叢集的實際 `node.name` 建立；`dist/` 只提供不含環境資料的 `expected-es-nodes.txt.example` 範本。

## 5. 打包後確認

```bash
(cd dist && shasum -a 256 -c *.sha256)
(cd dist && shasum -a 256 -c collectors/*.sha256)
file dist/elk-diagnostics-linux-amd64
file dist/elk-diagnostics-linux-arm64
git status --short --branch
```

驗收條件：

- 所有 checksum 顯示 `OK`。
- binary 架構與檔名一致。
- Git 工作區仍乾淨。
- 記錄本次 Git commit、打包日期、目標使用者與交付路線。

## 6. 建立 Route 專屬壓縮檔

不要直接壓縮整個 `dist/`。先依路線建立暫存目錄，再封裝。

Route B 範例（Linux amd64）：

```bash
COMMIT="$(git rev-parse --short HEAD)"
PACKAGE="dist/package-route-b-${COMMIT}"
ARCHIVE="elk-diagnostics-route-b-linux-amd64-${COMMIT}-$(date +%Y%m%d).tar.gz"

mkdir -p "$PACKAGE"
cp dist/elk-diagnostics-linux-amd64{,.sha256} "$PACKAGE/"
cp dist/API清單.md{,.sha256} dist/使用手冊.md{,.sha256} "$PACKAGE/"
cp dist/路線B-直連操作手冊.md{,.sha256} "$PACKAGE/"
cp dist/expected-es-nodes.txt.example{,.sha256} "$PACKAGE/"
cp dist/sbom.cdx.json{,.sha256} "$PACKAGE/"
cp config.yaml.example "$PACKAGE/"

tar -czf "$ARCHIVE" -C dist "$(basename "$PACKAGE")"
shasum -a 256 "$ARCHIVE" > "$ARCHIVE.sha256"
```

Route A 範例：

```bash
COMMIT="$(git rev-parse --short HEAD)"
PACKAGE="dist/package-route-a-${COMMIT}"
ARCHIVE="elk-diagnostics-route-a-${COMMIT}-$(date +%Y%m%d).tar.gz"

mkdir -p "$PACKAGE"
cp dist/collect.sh{,.sha256} "$PACKAGE/"
cp -R dist/collectors "$PACKAGE/collectors"
cp dist/API清單.md{,.sha256} dist/使用手冊.md{,.sha256} "$PACKAGE/"
cp dist/路線A-採集操作手冊.md{,.sha256} "$PACKAGE/"
cp dist/expected-es-nodes.txt.example{,.sha256} "$PACKAGE/"
cp dist/kibana-instances.conf.example{,.sha256} dist/logstash-instances.conf.example{,.sha256} "$PACKAGE/"

tar -czf "$ARCHIVE" -C dist "$(basename "$PACKAGE")"
shasum -a 256 "$ARCHIVE" > "$ARCHIVE.sha256"
```

壓縮檔與其 checksum 才是最終傳輸單位。產品介紹 PPTX 不屬於技術執行套件，需要時由業務文件流程另行提供。
